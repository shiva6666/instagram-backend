# ADR 0002: Image media upload and delivery lifecycle

- **Status:** Accepted; implemented in PR #13
- **Date:** 2026-11-16
- **Scope:** Image uploads and delivery in the active `backend/` application

## Context

The original post API accepted image URLs. That leaves file ownership, validation, storage, processing, and safe delivery outside the backend's control. The product needs a direct-upload flow that does not proxy large image bodies through FastAPI, while preserving existing URL-based posts.

PR #11 introduced an initial media foundation in the repository-root duplicate application. PR #13 closes the integration gap by implementing the complete lifecycle in the active `backend/` application used by the Dockerfile, CI, Makefile, and development launcher. The decisions below describe the active application.

## Decisions

### 1. Keep the modular monolith and make PostgreSQL authoritative

- Media is its own module under `backend/app/modules/media/`.
- Keep HTTP routing, application rules, persistence, image processing, and object storage behind separate boundaries.
- The media domain model is separate from HTTP schemas and SQLAlchemy rows.
- The repository exposes media operations; the service owns lifecycle and ownership rules.
- PostgreSQL stores metadata and relationships. Object storage stores bytes.
- Other modules use media service/resolver contracts rather than importing media ORM rows.

This keeps the first implementation understandable and testable without introducing microservices or a broker.

### 2. Upload bytes directly to private S3-compatible object storage

The API creates an upload ticket and a `PENDING` media row, then returns a short-lived presigned PUT URL. The browser sends bytes directly to MinIO/S3; the API does not stream the upload body.

- MinIO is the local S3-compatible implementation.
- The bucket remains private.
- Object keys are generated by the server and scoped by owner/media ID; client filenames are not used as storage paths.
- The storage adapter exposes an `ObjectStorage` interface and uses S3 Signature Version 4 without adding a new Python runtime dependency.
- Internal service calls use the Docker-network endpoint. Browser-facing presigned URLs use the public endpoint.
- Presigned upload URLs have a configured short TTL. Cleanup waits until the URL expiry plus a five-minute safety window before deleting an abandoned object.

### 3. Verify uploaded bytes; do not trust browser metadata

The upload request declares content type and byte size, but those values are not proof of the uploaded file.

- Accepted declared formats: JPEG, PNG, and WebP.
- The service enforces the configured maximum upload size and checks actual object size and stored content type.
- The processor sniffs file signatures and checks the decoded format against the declaration.
- Only one-frame images are accepted; animated/multi-frame images are rejected.
- Image dimensions are bounded (maximum 8,000 × 8,000 and 40 million pixels).
- ImageMagick runs with resource/time limits.
- The service creates a metadata-stripped WebP display variant (bounded to 1,600 × 1,600) and a 320 × 320 square thumbnail.
- Original filenames and client-supplied URLs are not used to determine the processed object's key.

### 4. Model media as an explicit lifecycle

The media state is persisted, not inferred from object existence:

`PENDING → PROCESSING → READY`

Validation/processing failures transition to `FAILED`. A failed upload can be retried through completion when it remains eligible. Cleanup is separately represented by a cleanup request timestamp and the `DELETING` state.

- A media row records its owner, expected and actual size, declared content type, upload expiry, object keys, dimensions, status, cleanup request, and failure reason.
- Completion is owner-checked and locks the media row before validating or changing it.
- Completing an already `READY` asset is idempotent.
- A media asset marked for cleanup cannot be completed or attached.
- Status and discard endpoints are authenticated and owner-scoped.

### 5. Attach only ready, owned, unattached media to posts

Post creation accepts either the legacy `post_img_url` field or the new `media_ids` field; the two forms are mutually exclusive.

For `media_ids`, the Post Service validates that each media record exists, belongs to the authenticated user, is `READY`, is not cleanup-requested, and is not already attached. Rows are locked during validation/attachment. A database uniqueness constraint on `post_media.media_id` is the final concurrency guard against attaching one media asset to multiple posts.

The post and media attachment are committed in the same PostgreSQL transaction. This makes post creation atomic with respect to its relational media links, but does not make object storage part of the database transaction.

### 6. Preserve legacy URL-based posts

Existing URL-based post creation and response behavior remains supported during migration. Existing `post_images` rows are migrated into media metadata and `post_media` relationships so existing posts retain their images.

This is a compatibility path, not a reason to expose newly uploaded objects as permanent public URLs. New storage-backed media uses signed delivery URLs.

### 7. Authorize before generating temporary read URLs

The bucket is private. Post and feed queries first apply their existing visibility/authorization rules. Only after a post is eligible for the requesting viewer does `MediaUrlResolver` mint short-lived signed GET URLs for its READY display objects.

- Never return a permanent public object URL for private media.
- Feed hydration batches media metadata rather than issuing one query per image.
- Legacy URL-backed images continue to resolve through their existing URL value.
- A post referencing media that is not READY is treated as an invalid persisted state.

### 8. Make cleanup retryable across the database/object-storage boundary

PostgreSQL and object storage cannot participate in one atomic transaction. Cleanup therefore uses a claim/delete/finalize sequence:

1. Claim eligible unattached media rows and set `DELETING` in PostgreSQL.
2. Use `FOR UPDATE SKIP LOCKED` so concurrent cleanup runs do not claim the same rows.
3. Commit the claim before making storage calls.
4. Delete original, display, and thumbnail objects idempotently.
5. Delete the metadata row only after object deletion succeeds and the asset is still unattached.
6. If storage deletion fails, leave the row in `DELETING`; a later run retries it.

Cleanup covers discarded media, abandoned pending/failed uploads after the grace period, and media attached to soft-deleted posts after the configured retention period. It waits until upload URLs have expired plus the safety window so a late PUT cannot recreate an orphan after cleanup.

Run the job periodically with `make cleanup-media`. It is intentionally a scheduled one-shot job rather than a continuously running worker.

### 9. Be conservative on schema downgrade

The media migration converts legacy image relationships into media records and a `post_media` join table. Downgrade must refuse when storage-backed media or uploaded media without a legacy URL remains attached, rather than silently converting a post into a broken URL-based image.

## End-to-end request flow

```mermaid
sequenceDiagram
    participant Browser
    participant API
    participant DB as PostgreSQL
    participant Store as Private MinIO/S3
    participant Processor as ImageMagick

    Browser->>API: POST /api/v1/media/upload-url
    API->>DB: Insert PENDING media row
    API-->>Browser: media_id + presigned PUT URL
    Browser->>Store: PUT image bytes
    Browser->>API: POST /api/v1/media/{id}/complete
    API->>DB: Lock row; verify owner/state
    API->>Store: HEAD object; GET bytes
    API->>Processor: Validate signature/decode/dimensions
    Processor-->>API: WebP display + thumbnail
    API->>Store: PUT processed variants
    API->>DB: Save READY + variant keys
    API-->>Browser: READY status
    Browser->>API: POST /api/v1/posts with media_ids
    API->>DB: Lock/validate media; insert post_media + post
    API-->>Browser: Post response
    Browser->>API: GET feed/post
    API->>DB: Apply visibility; hydrate media
    API->>Store: Sign GET URL after authorization
    API-->>Browser: Short-lived signed image URL
```

## API contract

| Operation | Endpoint | Purpose |
|---|---|---|
| Create upload ticket | `POST /api/v1/media/upload-url` | Declare content type and size; receive media ID and presigned PUT URL |
| Complete upload | `POST /api/v1/media/{media_id}/complete` | Verify object and process image |
| Read status | `GET /api/v1/media/{media_id}` | Read owner-scoped lifecycle status |
| Discard | `DELETE /api/v1/media/{media_id}` | Schedule unattached media for cleanup; returns 202 |
| Create post | `POST /api/v1/posts` | Attach READY assets using `media_ids`, or use legacy URL field |

## Consequences and trade-offs

### Benefits

- Large uploads bypass the API process.
- The backend controls object keys, ownership, validation, image variants, and delivery.
- Private storage plus post/feed authorization prevents public-bucket access from bypassing visibility rules.
- Explicit state and retryable cleanup make the lifecycle observable.
- Legacy URL support allows a gradual migration without breaking existing clients.
- Interfaces keep storage and processing replaceable and testable.

### Accepted limitations

- Image processing is synchronous inside upload completion in this first vertical slice. It is bounded, but slow processing holds the request open and may hold a database row lock/transaction while storage and processing work occurs.
- PostgreSQL cannot atomically commit object writes. A failure after setting `PROCESSING` or after writing only one variant can leave partial state/objects.
- The current happy-path MinIO end-to-end test does not prove every storage outage, malformed payload, expired URL, and retry scenario.
- Signed URLs are bearer capabilities until expiry; their TTL must remain short and they must not be logged.

## Follow-up work

1. Add MinIO-backed failure-path tests for invalid payloads, wrong size/content type, expired upload URL, storage outage, partial variant write, retry, and cleanup failure.
2. Add an explicit recovery path for stale `PROCESSING` records and partial processed objects.
3. Move image processing to a durable worker when traffic/latency justifies it. If moved, persist the processing request transactionally (e.g. outbox) and make the worker idempotent.
4. Revisit row-lock and transaction duration so external object-storage and image-processing calls do not hold a database transaction open longer than necessary.
5. Add operational metrics for pending/processing/failed/deleting counts, processing duration, cleanup backlog, and storage errors.
6. Add frontend upload UX (progress, retry, status polling) against the API contract.
