# Authentication Learning Notes

Concepts learned while designing authentication for this Instagram-style FastAPI backend.

> Status: learning/design notes. Authentication is not implemented yet. The current users module does not store password credentials.

---

## 1. Authentication vs. authorization

- **Authentication** answers: "Who is making this request?"
- **Authorization** answers: "Is this authenticated user allowed to perform this action?"

Example: authentication identifies the caller as user_101; authorization checks whether user_101 owns the post they want to delete. A valid token does not grant permission to perform every operation.

---

## 2. Passwords: hash, don't encrypt

Do not store passwords as plaintext or encrypt them for later decryption. Store a password hash generated by a password-hashing algorithm such as **Argon2id**.

### Registration

1. Client sends the password to the API over HTTPS.
2. Server validates the request.
3. Server hashes the password using Argon2id, which generates a random salt and uses configured parameters.
4. Server stores the encoded password hash, not the original password.

The encoded Argon2 hash contains the salt and parameters needed for later verification.

### Login

1. Client sends the entered password over HTTPS.
2. Server loads the user's stored password hash.
3. Server calls the password library's verification function with the entered password and stored hash.
4. The library verifies whether the password matches.

~~~python
if password_hasher.verify(stored_hash, incoming_password):
    # Password is correct
    ...
~~~

Do **not** hash the incoming password and compare hash strings with equality. Password hashing uses a random salt, so hashing the same password again normally produces a different encoded hash. Use the library's verify function.

Password verification happens at login (and when verifying a current password for a sensitive action such as changing it), **not on every authenticated API request**.

Use Argon2id for human-chosen passwords. Do not use fast general-purpose hashes such as plain SHA-256 for password storage.

## 3. Keep authentication credentials separate from the user profile

The current users domain model represents the person's profile: username, email, bio, privacy setting, status, and timestamps. It does not contain a password.

A useful design is a separate auth_identities table:

| Field | Purpose |
|---|---|
| id | Identity record ID |
| user_id | Reference to the application user |
| provider | For example, password or google |
| provider_user_id | Identifier assigned by an external provider, where applicable |
| password_hash | Argon2id hash for password identities; null for social identities |
| created_at | Creation timestamp |

This allows one user to have multiple authentication methods without putting credential-specific fields into the profile model. Enforce uniqueness for provider/provider-user-ID pairs.

## 4. What is a JWT?

A JSON Web Token (JWT) is a compact, signed token. A typical signed JWT has three Base64URL-encoded parts:

~~~text
header.payload.signature
~~~

Example payload (illustrative):

~~~json
{
  "sub": "user_101",
  "iss": "instagram-backend",
  "aud": "instagram-api",
  "iat": 1794100000,
  "exp": 1794100900,
  "jti": "unique-token-id"
}
~~~

Common claims:
- sub: subject; in this application, the user ID.
- iss: issuer; which trusted system issued the token.
- aud: intended audience.
- iat: issued-at time.
- exp: expiration time.
- jti: token identifier, useful for tracking or revocation designs.

JWT payloads are **encoded, not encrypted**. Anyone who obtains a normal signed JWT can decode and read its claims. Do not put passwords, signing keys, or sensitive private data in the payload.

---

## 5. How JWT signatures work

The signature protects the header and payload from undetected modification and lets a verifier check that the token was signed by a trusted key.

### HS256 (symmetric signing)

- The same secret key signs and verifies the token.
- Every service that can verify with this shared secret can also create valid signatures.
- Keep the secret out of source control; load it from secure configuration or secrets management.

Conceptually:

~~~python
signature = HMAC_SHA256(
    secret_key,
    encoded_header + "." + encoded_payload,
)
~~~

### RS256 (asymmetric signing)

- The authentication service signs with a private key.
- Other services verify with the corresponding public key.
- Services holding only the public key cannot create valid signatures.

This can be useful when multiple services need to verify tokens but should not all possess signing capability.

### What makes a token belong to a user?

The signature is **not a unique signature registered per user**. The issuer signs each token using its signing key. The verified payload contains the user's ID in sub.

For each request, the API:
1. Extracts the bearer token.
2. Verifies its signature using a configured, explicitly allowed algorithm.
3. Validates required claims such as iss, aud, and exp.
4. Reads sub from the verified payload.
5. Loads the corresponding user (or otherwise checks the user's current status) as required by policy.

The server does not need a database row mapping every access-token signature to a user.

**Important:** A valid signature proves the token was signed by a trusted key and was not modified. It does not prove the current presenter is the original person. If someone steals a valid, unexpired bearer token, they can generally use it. Protect tokens with HTTPS and secure client-side storage.

## 6. Access tokens: normal API requests

After successful login, issue a short-lived access JWT.

Example:

~~~http
GET /posts
Authorization: Bearer <access-token>
~~~

A FastAPI dependency (for example, get_current_user) can:
- Extract and validate the access token.
- Check signature, algorithm, issuer, audience, and expiration.
- Extract sub.
- Load the corresponding user and reject missing, disabled, or deleted users according to policy.
- Return the authenticated user to the route.

The route can then apply authorization rules, such as checking post ownership.

Access-token expiration is carried in the JWT's exp claim. The verifier compares it with the current time (allowing only a small configured clock-skew leeway). A database lookup is not required just to check JWT expiry.

A short access-token lifetime (for example, 10–15 minutes) limits the usefulness window of a stolen token. It does not by itself provide immediate revocation.

## 7. Refresh tokens: obtain new access tokens

The access token is short-lived so that a stolen token has a limited lifetime. The refresh token lets a user obtain a new access token without entering their password again.

Recommended initial design for this project:
- Access token: signed JWT with a short expiry.
- Refresh token: opaque, cryptographically random value (not necessarily a JWT).
- Store only a hash/fingerprint of the refresh token in PostgreSQL.
- Send the raw refresh token to the client only when issuing it.

### Example refresh-token table

refresh_tokens:

| Field | Purpose |
|---|---|
| id | Refresh-token record ID |
| user_id | Owner |
| family_id | Groups tokens belonging to one login/session chain |
| token_hash | Hash/fingerprint of the raw random token |
| created_at | When issued |
| expires_at | Absolute expiry timestamp |
| revoked_at | When invalidated, if applicable |
| replaced_by_token_id | Optional link to the successor token |

Refresh tokens should have high cryptographic entropy. Because they are random machine-generated secrets rather than human-chosen passwords, a fast cryptographic hash such as SHA-256 (or a keyed HMAC with a separately protected server key) is suitable for storing a fingerprint. Argon2id is intended for low-entropy human passwords.

### Refresh flow

1. Client sends the refresh token to POST /auth/refresh.
2. Server hashes/fingerprints the presented token and finds its record.
3. Server checks that the record exists, is not expired, and is not revoked/consumed.
4. Server issues a new short-lived access JWT and a new refresh token.
5. Server invalidates the old refresh token and stores the new token's hash.
6. Client uses the new access token for API calls and retains the new refresh token.

The password is not checked again during refresh. The refresh credential is validated instead.

### Why rotation matters

Suppose a login session starts with refresh token RT-001.

- Shiv uses RT-001 and receives RT-002.
- RT-001 is marked consumed/revoked.
- If RT-001 is presented again later, it is a reuse event. It may indicate that an attacker copied the old token.
- A robust policy revokes the entire refresh-token family and requires a fresh login.

Rotation and reuse handling should be implemented transactionally to prevent concurrent refresh requests from both successfully consuming the same token. The client should also coordinate refresh attempts so multiple simultaneous API failures do not race to refresh.

## 8. Expiration is different from theft detection

A token's signature does not tell the server whether the token has been stolen.

| Check | What it answers |
|---|---|
| Signature verification | Was this token signed by a trusted issuer and left unmodified? |
| Expiration | Is it past its allowed lifetime? |
| Revocation state | Has the token/session been invalidated? |
| Refresh-token reuse detection | Is an already-consumed refresh token being presented again? |

For refresh tokens, store an absolute expires_at timestamp. It can be calculated at issuance:

~~~python
created_at = datetime.now(timezone.utc)
expires_at = created_at + timedelta(days=7)
~~~

Storing created_at and expires_at is useful for auditability; checking expires_at is straightforward and avoids recalculating the policy on each validation. Use timezone-aware UTC timestamps.

A stolen, still-active refresh token cannot be identified merely by inspecting it. Rotation can detect reuse after the legitimate client has already consumed it, but cannot guarantee detection before that.

## 9. Logout and revocation

Logout should revoke the relevant refresh token (or its whole family) and clear the client's stored credentials.

A stateless access JWT may remain valid until its exp time. If immediate access-token revocation is required, add a mechanism such as:
- A short-lived access-token policy plus refresh-token revocation (often sufficient for a first version).
- A jti denylist checked on each request.
- A user/session token-version or session-state check.

Each option adds state/lookups and should be chosen deliberately.

## 10. Browser and mobile token storage

For a browser client:
- Prefer a refresh token in a Secure, HttpOnly, appropriately SameSite cookie.
- Protect cookie-authenticated refresh/logout endpoints against CSRF (for example, an appropriate CSRF token and origin checks).
- Avoid persistent browser storage for long-lived bearer credentials where practical.
- Keep HTTPS enabled.

For a native mobile client, store refresh credentials in platform secure storage (Keychain/Keystore). Avoid logging tokens.

## 11. Sessions vs. JWTs and future service distribution

JWT is not mandatory just because an application may later be split into services.

### Server-side sessions

- Client holds an opaque session ID in a cookie.
- Server stores session state in a shared store such as Redis or PostgreSQL.
- Every service that needs the session must be able to access/validate that shared state, or trust a gateway that validates it and securely propagates identity.
- Revocation is straightforward because the server controls the session record.

An in-memory-only session store breaks across multiple instances unless requests are pinned to the same instance. Sticky sessions are a workaround, but a shared session store is generally more robust.

### JWT access tokens

- Services can verify signed claims locally without a shared lookup on every request.
- Services must securely receive and rotate trusted verification keys and validate claims consistently.
- Immediate revocation is harder without additional shared state.

Choose based on client needs, revocation requirements, and operational complexity—not simply because microservices might exist in the future. This project is currently a modular monolith; keep the first implementation simple.

## 12. Pydantic schemas vs. domain models vs. ORM models

These are related but have different responsibilities.

| Concept | Responsibility | Example |
|---|---|---|
| API schema (Pydantic) | Validates request data and shapes response data | RegisterRequest, LoginRequest, TokenResponse |
| Domain model | Represents a business concept without framework coupling | Immutable User dataclass |
| ORM model | Maps data to database tables/columns | SQLAlchemy UserRow, RefreshTokenRow |

For example:
- RegisterRequest accepts username, email, and password.
- The auth service validates the request and hashes the password.
- A domain object represents the identity/user concepts used by business logic.
- The repository maps domain data to SQLAlchemy rows and persists it.
- A response schema returns only safe fields/tokens—not password hashes.

This follows the existing users module's separation of domain, service, repository, and persistence concerns.

---

## 13. Suggested auth module structure

~~~text
app/modules/auth/
    schemas.py       # Pydantic request/response schemas
    models.py        # Pure domain objects, if needed
    repository.py    # Repository protocol and SQLAlchemy adapter
    service.py       # Register, login, refresh, logout use cases
    tokens.py        # Password hashing, JWT and opaque-token helpers
    dependencies.py  # get_current_user and auth dependencies
~~~

Keep SQLAlchemy row classes in the persistence/adapter layer (or a clearly separated ORM module) rather than confusing them with pure domain models. Follow the existing users module's conventions.

## 15. Key takeaways

- Passwords are verified against stored Argon2id hashes only at login; they are not sent with every request.
- The access JWT carries a user identifier (sub) and is protected by a signature.
- The signing key belongs to the issuer/application, not uniquely to each user.
- Signature verification proves trusted issuance and integrity, not that the presenter is the original user.
- Access-token expiry is checked from the JWT's exp claim.
- Refresh-token expiry/revocation is checked against server-side state.
- Refresh-token rotation limits replay and enables reuse detection.
- Schemas, domain models, and ORM models are separate concepts.
- Sessions can also work in distributed systems when session state is shared; JWT is a trade-off, not a requirement.
